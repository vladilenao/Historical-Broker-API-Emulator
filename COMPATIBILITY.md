# Совместимость с роботом (My_roBot)

> **Текущий My_roBot несовместим с HTTP API эмулятора до своей миграции.** Он
> обращается к UID-маршрутам, совместимым с Tinkoff API; сервер сохраняет их
> без изменений и одновременно принимает публичную пару `instrument_type + ticker`.
> План перехода: [docs/robot-api-migration-spec.md](docs/robot-api-migration-spec.md).
> Таблица ниже — историческая фиксация прежней интеграции, а не описание текущих
> HTTP-маршрутов.

Таблица соответствия между тем, что ожидает робот (`../My_roBot`, read-only), и
тем, что фактически реализует этот эмулятор. Подробности — в
[`docs/existing_robot_api_analysis.md`](docs/existing_robot_api_analysis.md) и в
OpenAPI-спецификации сервера.

| Ожидание робота | Реализация эмулятора | Статус |
|---|---|---|
| Свечи как DataFrame с колонками `datetime, open, high, low, close, volume` | `GET /api/v1/candles` возвращает строки ровно с этими полями в этом порядке | ✅ |
| `datetime` — naive UTC | Все даты хранятся/отдаются как naive UTC `YYYY-MM-DD HH:MM:SS` (формат снапшотов робота) | ✅ |
| `open/high/low/close` — `float` в духе `units + nano/1e9` | Числа (JSON float) | ✅ |
| `volume` — целое | Целое | ✅ |
| Порядок свечей по времени | `ORDER BY ts ASC`, детерминированно | ✅ |
| Таймфреймы ровно `1m 5m 15m 30m 1h 4h 1d 1w 1M` | Тот же набор; иное → `INVALID_INTERVAL` | ✅ |
| Без агрегации `1m → 5m/…` (каждый таймфрейм скачивается напрямую) | Хранение и отдача «как есть», без агрегации | ✅ |
| Поиск инструмента по `ticker + instrument_type` | `GET /api/v1/instruments?ticker=&instrument_type=`, типы `share/future/etf/currency` | ✅ |
| Идентификация инструмента по Tinkoff `uid` (`instrument_id`) | `instrument_id` — первичный идентификатор во всех endpoints | ✅ |
| Чанкинг запросов по лимитам SDK (`get_intervals`) | Тот же чанкинг в `history download` | ✅ |
| Ретраи при `RESOURCE_EXHAUSTED` (+`ratelimit_reset`), переоткрытие потока свечей | Реализованы в `src/tinkoff/` и `src/tinkoff/downloader.py` | ✅ |
| Диапазоны запросов от/до (включительные) | `[from, to]` включительно на обеих границах | ✅ |
| Подготовка истории из Tinkoff Invest API (вне клиента робота) | CLI `historical-broker history download`; HTTP `downloads*` реализован | HTTP ✅ |
| История недоступна — понятная ошибка | `INSTRUMENT_NOT_FOUND` / `HISTORY_NOT_AVAILABLE` | ✅ |
| Токен не логируется | Токен никогда не выводится в лог | ✅ |

## Метаданные контрактов

Робот отклоняет каждый сигнал с причиной `no-contract-metadata`, если в карточке
инструмента нет этих полей, а фьючерсы не проходят отбор по экспирации
(«Нет фьючерсов с экспирацией в ближайшие 6 месяцев»). Все они заполняются при
синхронизации каталога и отдаются в обоих `instruments`-эндпоинтах.

| Поле | Источник | Формат в ответе |
|---|---|---|
| `figi` | `FIGI` из Tinkoff | строка |
| `min_price_increment_amount` | фьючерсы — из Tinkoff; акции — `min_price_increment × lot` | float |
| `initial_margin_on_buy` / `initial_margin_on_sell` | `initial_margin_on_*`, иначе `dlong`/`dshort` | float |
| `expiration_date` | только у фьючерсов; у акций `null` | ISO 8601 со смещением `+00:00` |

`expiration_date` — единственное исключение из правила наивного UTC: именно в
таком виде (со смещением) живой Tinkoff API отдаёт дату, и так её разбирает
`schemas.Future` из SDK.

Фьючерсы и акции отдаются из **разных** моделей Tinkoff: у акций нет ни
экспирации, ни `initial_margin_on_*` (есть только `dlong`/`dshort`), и
`min_price_increment_amount` приходится считать. Это учтено в
`src/tinkoff/client.py::list_instruments`.

## Большие диапазоны

Робот читает уже подготовленные свечи; HTTP API скачивания он не вызывает.
Старые маршруты `download` и `jobs*` удалены. Публичный API загрузки —
`/api/v1/history/downloads*`. Фоновый исполнитель
`DownloadJobStore` остаётся внутренним Python-сервисом.

| Потребность | Реализация |
|---|---|
| Статус и результат загрузки | Проектируемые `GET /api/v1/history/downloads/{download_id}` и `/report` |
| Не ждать скачивание | Проектируемый `POST /api/v1/history/downloads` отвечает `202` сразу |
| Прервать и продолжить | Проектируемые `POST .../cancel` и `POST .../retry` |
| Идемпотентность | Повторный идентичный запрос в `downloads` возвращает тот же ресурс (planned) |
| Проверить глубину истории до прогона | `GET /api/v1/coverage?instrument_id=&interval=&from=&to=` → `from`, `to`, `count` |
| Много пар за один запрос | `POST /api/v1/candles/batch` — до 256 подзапросов, ошибка одного не роняет остальные |

## Контракт, который робот НЕ требует (осознанно не реализовано)

- Торговля: заявки, песочница, счета, портфели, стримы сделок.
- Стриминговые рыночные данные.
- Полное зеркалирование каталога инструментов.
- Технический анализ и оценка стоимости в API.

## Известные ограничения на стороне робота

Эмулятор отдаёт метаданные корректно, но текущий адаптер робота
(`../My_roBot/src/api/emulator_client.py`) их частично игнорирует — это
**не** ограничение эмулятора, а то, что нужно поправить в роботе:

- `_instrument()` жёстко ставит `expiration_date = None`, из-за чего фьючерсы не
  проходят отбор по экспирации. Эмулятор уже отдаёт дату в ISO 8601 `+00:00`;
  адаптеру достаточно её прочитать вместо `None`.
- `get_futures_margin()` возвращает нулевые `initial_margin_on_buy/sell` и
  подставляет шаг цены вместо стоимости шага. `load_futures_contracts` берёт ГО
  именно оттуда, поэтому даже при исправленном `_instrument()` контракт получает
  `go_buy = go_sell = 0.0`. Эмулятор отдаёт реальные значения в карточке
  инструмента (`min_price_increment_amount`, `initial_margin_on_*`), поэтому
  адаптеру достаточно перестать подменять их заглушкой.
- `load_futures_contracts` записывает `expiration_date = to_naive(inst.expiration_date)`,
  поэтому `None` из `_instrument()` превращается в `NaT`. Контракт попадает в кэш,
  но с невалидной датой и обнулённой ГО, и отбор по экспирации его отбрасывает
  («Нет фьючерсов с экспирацией в ближайшие 6 месяцев»).
- `run.py::_load_contracts_metadata` идёт в `client_context()` (живой Tinkoff SDK)
  и требует `TINKOFF_TOKEN`, а не в `EmulatorClientProvider`; из-за этого кэш
  контрактов пуст и входы отклоняются с `no-contract-metadata`.

Пока эти три пункта не исправлены в роботе, совместный прогон не заработает
независимо от состояния эмулятора.

## Автономность

Пока `TINKOFF_TOKEN` не настроен, сервер стартует и все read-only endpoints
работают. Только маршруты `/api/v1/history/*` возвращают
`AUTHENTICATION_ERROR` (401).

(`tests/unit/test_openapi.py`).
