# Historical Broker API Emulator — Distribution Build

Продолжай работу с уже реализованным проектом **Historical Broker API Emulator**.

Приложение уже реализовано, документировано и протестировано.

Теперь необходимо подготовить полноценный пользовательский дистрибутив, который можно перенести на другой компьютер и запустить без установки Python и без ручной установки зависимостей.

Не изменяй бизнес-логику приложения без необходимости.

---

# 1. Цель

Подготовить standalone-дистрибутив Historical Broker API Emulator.

Пользователь должен иметь возможность:

1. распаковать дистрибутив;
2. при необходимости заполнить конфигурацию;
3. запустить приложение;
4. открыть Swagger;
5. загрузить исторические данные;
6. использовать локальный API.

На целевой машине не должно требоваться:

* установленного Python;
* `pip install`;
* виртуального окружения;
* ручной установки Python dependencies.

---

# 2. Анализ текущего проекта

Перед настройкой сборки определить:

* точку входа приложения;
* способ запуска HTTP API;
* используемый framework;
* используемые CLI-команды;
* расположение SQLite database;
* расположение конфигурации;
* использование `.env`;
* наличие статических файлов или templates;
* runtime dependencies;
* файлы, которые должны находиться рядом с executable.

Не менять существующие интерфейсы приложения без необходимости.

---

# 3. Формат дистрибутива

Если проект написан на Python, предпочтительно использовать:

```text
PyInstaller
```

если нет объективной причины выбрать другой инструмент.

Подготовить reproducible build configuration.

Предпочтительно создать:

```text
historical_broker_api_emulator.spec
```

или аналогичный PyInstaller `.spec` файл.

Не ограничиваться ручной командой PyInstaller.

Конфигурация сборки должна храниться в репозитории.

---

# 4. Результат сборки

После сборки должен появляться каталог примерно такого вида:

```text
dist/
└── historical-broker-api-emulator-vX.Y.Z/
    ├── historical-broker-api-emulator.exe
    ├── config/
    ├── data/
    ├── logs/
    ├── .env.example
    ├── README.txt
    ├── API_CONNECTION.md
    ├── COMPATIBILITY.md
    └── VERSION.txt
```

Это пример структуры.

Адаптируй её к реальному приложению и целевой ОС.

Не включай настоящий `.env` с секретами.

Не включай Tinkoff API token.

---

# 5. Версия приложения

Добавь единый источник версии приложения, если его ещё нет.

Использовать SemVer:

```text
MAJOR.MINOR.PATCH
```

Например:

```text
0.1.0
```

Версия должна быть доступна:

* из кода приложения;
* при сборке;
* в имени дистрибутива;
* в `VERSION.txt`.

По возможности добавить:

```bash
historical-broker-api-emulator --version
```

или эквивалентный механизм.

Не дублировать номер версии вручную в нескольких независимых местах.

---

# 6. Runtime directories

Приложение после упаковки должно корректно работать вне исходного репозитория.

Особенно проверить пути к:

* SQLite database;
* logs;
* config;
* `.env`;
* OpenAPI-related resources;
* другим runtime-файлам.

Нельзя полагаться на:

```text
current working directory == repository root
```

Приложение должно определять свои runtime paths предсказуемо.

Предпочтительно данные пользователя хранить отдельно от встроенных ресурсов приложения.
