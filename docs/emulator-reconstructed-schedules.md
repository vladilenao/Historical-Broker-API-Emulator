
## Зачем

Сессионная защита внутридневных сделок (`session.intraday`) без расписания
запрещает вход (`session-schedule-unknown`). Брокер не отдаёт расписание
прошедших дат, а My Robot записывает его только с момента запуска записи
(сейчас это 2026-10-13 — 2026-10-24). Поэтому в историческом прогоне BR за
2025-03-10 — 2025-09-10 все 910 сигналов стратегий `future-br-macd` и
`future-br-ma` были отклонены, торговали только часовые стратегии.

Нужно, чтобы эмулятор хранил для прошедших дат **восстановленное**
расписание рядом с подтверждённым (из ленты My Robot), явно помечал его
происхождение и отдавал роботу тем же эндпоинтом.

## Что уже есть

- Импорт ленты `GET /api/v1/market-data/trading-schedules` с отдельным
  курсором, таблицы `imported_schedule_days` и `imported_schedule_bindings`,
  общий счётчик `snapshot_generation`.
- `GET /api/v1/trading-schedules?instrument_id&from&to&snapshot_generation`
  отдаёт `days` с `provenance: "my_robot_export"` и `missing_dates`.
- День хранится в каноническом JSON My Robot, `version = sha256(raw_json)`;
  робот пересчитывает версию и сверяет её.

Ограничение текущей схемы: привязки `instrument_uid → exchange` есть только
у инструментов, которые робот видел в live. У прошлых контрактов (`BRJ5` …
`BRV5`) привязки нет, и эндпоинт отдаёт `exchange: null` и пустой `days`.

## Что сделать

### 1. Хранение

Отдельные таблицы, не смешанные с лентой My Robot (у импорта свой курсор
`producer_id`/`change_id`, а восстановленные строки к ленте не относятся):

- `reconstructed_schedule_days`: `exchange`, `trading_date`, `version`,
  `raw_json`, `is_trading_day`, `rules_version`, `generated_at`,
  `generation`;
- `reconstructed_schedule_bindings`: `instrument_uid`, `exchange`,
  `rules_version`, `generated_at`, `generation`.

Строки не перезаписываются: новый запуск генератора добавляет новые версии в
новом поколении, старые снимки воспроизводятся как были. Сброс базы
восстановленные строки не трогает так же, как импортированные.

### 2. Правила сессий — данные, а не код

Файл правил (например, `config/schedule_rules/forts_futures_weekend.toml`) с
версией и периодами действия. Каждый период задаёт окна по МСК для будней и
для выходных (или их отсутствие) с типами интервалов как у брокера.

По свечам BR в базе эмулятора (1m, 2025-03 — 2025-09, МСК) видно:

| Что | Будни | Выходные |
|---|---|---|
| Первый бар | 08:59 (аукцион открытия) | 09:59–10:00 |
| Перерыв | нет баров 14:00–14:04 (клиринг) и 18:50–19:04 (вечерний клиринг) | — |
| Последний бар | 23:49 | 18:51–18:59 |
| Утренняя сессия 07:00 | нет | — |
| Сессии выходного дня | — | с 2025-08-16 |

Отсюда первые периоды правил:

- **до 2025-08-15:** будни — `opening_auction` 08:50–08:59:59,
  `regular_trading_session_main` 09:00–18:49:59,
  `regular_trading_session_evening` 19:05–23:50:00; выходные неторговые;
- **с 2025-08-16:** то же плюс выходные — аукцион открытия 09:50–09:59:59,
  `holiday_trading_session_morning` 10:00–19:00.

Текущее расписание брокера (2026-10) другое: утренняя сессия 07:00–08:59:59,
основная 09:00–18:59:59, вечерняя 19:00–23:50. Когда режим сменился, нужно
установить по отчёту генератора (раздел 6), а не угадывать. Дневной клиринг
14:00–14:05 брокер в расписании не показывает, и восстановленный день его тоже
не содержит: робот ведёт клиринг по `[trading].clearing_times`.

### 3. Какие даты торговые

- Торговость даты определяется по барам инструментов, привязанных к режиму
  торгов. Нужно несколько ликвидных инструментов, чтобы дыра в данных одного
  контракта не превратилась в праздник. Дата без баров —
  `is_trading_day=false` без интервалов. Дата с неполными барами — торговая,
  но попадает в отчёт.
- Выходной день становится торговым только в периоде, где правила разрешают
  сессии выходного дня. Бары в выходной вне такого периода — расхождение для
  отчёта.
- Окна берутся **из правил**, а не подгоняются по барам каждого дня. Бары
  только определяют, торговый ли день, и проверяют правила. Это не
  заглядывание вперёд: биржа публикует расписание заранее, и неторговый день
  был известен до его начала.

### 4. Формат дня

- Полный `TradingDay` со всеми полями SDK в каноническом JSON My Robot:
  - ключи отсортированы, время UTC вида `YYYY-MM-DDTHH:MM:SS.ffffffZ`;
  - пустые времена — `1970-01-01T00:00:00.000000Z`;
  - интервалы продублированы родовым и конкретным типом, как у брокера
    (`opening_auction` + `opening_auction_morning`,
    `regular_trading_session` + `regular_trading_session_main` и т. д.);
  - заполнены `start_time`, `end_time`, `opening_auction_*`, `clearing`.
- `version = sha256(raw_json)`, та же проверка, что при импорте.
- Эталонный тест: сгенерировать по правилам текущего режима даты, для которых
  есть дни из ленты My Robot (2026-10-13 — 2026-10-24), и сравнить версии.
  Они должны совпасть. Если в чём-то совпасть не могут, разница перечисляется
  в тесте явно.

### 5. Привязки прошлых контрактов

Для инструментов из `instruments` без импортированной привязки создать
восстановленную привязку по `class_code`/`instrument_type`. Например,
`SPBFUT` + `futures` → `forts_futures_weekend`; таблица соответствий входит в
файл правил. Импортированная привязка всегда главнее восстановленной.

### 6. Генератор и отчёт

Команда CLI, например
`reconstruct-schedules --exchange forts_futures_weekend --from 2025-01-01 --to 2026-10-12 [--dry-run]`:

- пишет все дни и привязки одной транзакцией в одном новом поколении;
  `--dry-run` только печатает отчёт;
- не создаёт восстановленный день там, где уже есть день из ленты My Robot;
- отчёт:
  - число торговых, неторговых и выходных торговых дней;
  - неполные дни;
  - бары вне окон правил и окна правил без баров;
  - помесячно первый и последний бар будней и выходных — по этой таблице
    уточняются периоды правил.

### 7. API

`GET /api/v1/trading-schedules`:

- для каждой даты берётся день из ленты My Robot, видимый в поколении, а если
  его нет — восстановленный день;
- привязка выбирается с тем же приоритетом;
- у дня есть поля `provenance` (`my_robot_export` или `reconstructed`) и
  `rules_version` (только у восстановленных); `source` у восстановленных —
  `emulator-reconstructed`;
- `missing_dates` — только даты, для которых нет ни того, ни другого;
- закрепление за `snapshot_generation` работает и для восстановленных строк.

### 8. Тесты

- канонический JSON и версия восстановленного дня совпадают с днём брокера
  (эталон из раздела 4);
- приоритет: день и привязка из ленты главнее восстановленных, в том числе
  если лента пришла позже генерации;
- снимок, выданный до генерации, не видит восстановленных дней; снимок после —
  видит;
- праздник (будний день без баров) — `is_trading_day=false`; дыра в одном
  контракте при барах других — торговый день с пометкой в отчёте;
- выходные до и после 2025-08-16;
- прошлый контракт без импортированной привязки получает восстановленную;
- повторный запуск генератора с теми же правилами не создаёт новых версий,
  с новыми — создаёт;
- `--dry-run` ничего не пишет.

## Не входит в задачу эмулятора

Доработка робота — отдельная задача:

- читать `provenance` и `rules_version`;
- сессионная защита работает по восстановленным дням, в трассе
  `session.intraday` видно происхождение дня;
- восстановленные дни **не** служат доказательством планового отсутствия
  свечей;
- отчёт прогона показывает, сколько дней пришло из ленты, сколько
  восстановлено, сколько без расписания, и недопуски по стратегиям; при
  отсутствии расписания — только предупреждение.

## Готово, когда

- после генерации за 2025 год запрос робота по UID `BRJ5` … `BRV5` возвращает
  дни с `provenance: "reconstructed"`, а `missing_dates` за эти даты пуст;
- за 2026-10-13 — 2026-10-24 возвращаются дни из ленты My Robot;
- эталонный тест версии проходит;
- отчёт генератора за 2025 год не содержит необъяснённых расхождений;
- все тесты эмулятора зелёные.
