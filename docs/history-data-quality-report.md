# Отчёт качества исторических данных

## Доступный API

```text
POST /api/v1/history/data-quality/report
```

Отдельный read-only отчёт эмулятора. Работает офлайн по локальной SQLite-базе,
не скачивает данные у Tinkoff и не изменяет контракт `GET /api/v1/coverage`.
Описание запроса, ответов и примеры доступны в Swagger `/docs`, ReDoc `/redoc`
и `docs/openapi.yaml` (именно этот файл обслуживает `/openapi.json`).

Публичный ключ — `instrument_type + ticker`, как в новом API инструментов.
UID используется только внутри сервера. Передавайте тикер из каталога:
человекочитаемое имя фьючерса и его биржевой тикер могут отличаться.

## Пример запроса

```bash
curl -X POST http://127.0.0.1:8100/api/v1/history/data-quality/report \
  -H 'Content-Type: application/json' \
  -d '{
    "requests": [
      {
        "instrument_type": "share",
        "ticker": "SBER",
        "interval": "1h",
        "from": "2025-01-15T10:00:00Z",
        "to": "2025-01-15T18:59:59Z",
        "warmup_bars": 2
      }
    ],
    "sample_limit": 20
  }'
```

Один запрос принимает от 1 до 256 пар/участков. Каждая пара содержит собственные
границы и число баров прогрева. Для контрактной цепочки передайте конкретный
контракт на каждом назначенном участке; эмулятор не выбирает политику ролловера.
Все результаты возвращаются в порядке `requests`.

`from` и `to` включительны. Время со смещением приводится к UTC; дата без времени
означает начало дня для `from`, конец дня для `to`. Требуется точность до целой
секунды. В ответе нормализованные моменты имеют вид `YYYY-MM-DD HH:MM:SS`.
Для робота с полуинтервалом `[start, end)` передайте в `to` последнюю допустимую
секунду перед `end`, чтобы не включить свечу, открывшуюся на исключённой границе.

## Снимок и воспроизводимость

Необязательный `snapshot` — непрозрачный токен публичного API чтения, а не
внутренний номер `snapshot_generation`. Можно использовать снимок из каталога
или предыдущего чтения. Если токен не передан, эмулятор создаёт новый.

Отчёт возвращает `snapshot`; передайте его в последующее чтение свечей.
Все пары анализируются на одной версии каталога и истории. Исправления свечей
и последующая загрузка не меняют результат старого снимка. После перезапуска
процесса токены недействительны; нужно получить новый снимок.

## Что проверяется

| Проверка | Результат |
|---|---|
| Наличие истории | `count`, `first`, `last` внутри диапазона |
| Прогрев | Последние N фактически закрытых свечей перед `from`; `warmup.available`, `invalid_count`, `satisfied` |
| Цены | Конечные числовые OHLC; `low <= open/close <= high`. Отрицательная цена допустима |
| Объём | Целое неотрицательное значение |
| Время | Каноническая существующая дата UTC до секунды; начало на целой минуте; месячная свеча — первое число месяца в 00:00 |
| Паузы | Интервал между ожидаемым следующим открытием и фактически следующим открытием |
| Края | Наблюдаемое начало позже запроса или отсутствие хвоста; причина отсутствия свечей не утверждается |

Каждый таймфрейм проверяется независимо: минутные свечи не доказывают корректность
часовых. Дубли по ключу `(instrument_id, interval, ts)` запрещены схемой SQLite;
для версий берётся последняя версия ключа не новее снимка.

`warmup_bars` по умолчанию 0, максимум 100 000. Бар прогрева считается закрытым,
если его открытие плюс интервал не позже начала диапазона. Для `1M` используется
календарный месяц, не 30 дней. Некорректный бар среди последних N не заменяется
более старым: такой прогрев получает `INSUFFICIENT_WARMUP`.

Для пауз также используется длительность данного интервала; для `1M` —
следующий календарный месяц. `pause_from` — ожидаемое следующее открытие,
`following` — фактическое открытие после паузы. `duration_seconds` — разница
между ними. Для некорректных временных меток паузы не вычисляются.

## Статусы и интерпретация

| `status` | Значение |
|---|---|
| `not_ready` | Нет свечей, выявлены дефекты, не хватает корректного прогрева либо ошибочна пара/диапазон |
| `warning` | Есть наблюдаемые паузы или неподтверждённые края; их причины не установлены |
| `unknown` | Явные проблемы не найдены, но полная целостность не подтверждена |

Общий статус выбирается по приоритету `not_ready > warning > unknown`.
HTTP 200 означает, что отчёт построен, а не что данные пригодны без оговорок.
Читайте `results[*].status` и `issues`.

**`completeness` всегда `unknown` в этой реализации.** Здесь ещё нет полного
биржевого календаря и подтверждённых причин отсутствия свечей. Ночи, выходные
и отсутствие сделок не объявляются потерянными данными. `ready` намеренно не
выдаётся. `MIN/MAX/COUNT` и отсутствие пауз не доказывают полноту истории;
арифметика `slots - count` не используется.

Импортированные состояния `scheduled_closed`, `confirmed_no_trade`, `pending`,
`unresolved` сейчас не используются для положительного вердикта: их необходимо
согласовать с календарём, источником и версией снимка отдельной доработкой.

Основные коды `issues`: `COMPLETENESS_UNKNOWN`, `OBSERVED_PAUSES`,
`START_NOT_CONFIRMED`, `END_NOT_CONFIRMED`, `NO_CANDLES`, `INVALID_CANDLES`,
`INSUFFICIENT_WARMUP`. Примеры дефектных свечей содержат `INVALID_TIMESTAMP`,
`INVALID_OHLC`, `INVALID_VOLUME`.

## Размер отчёта и стоимость

`sample_limit` — от 0 до 100, по умолчанию 20. Он отдельно ограничивает списки
`pauses` и `invalid_samples` каждой пары. Паузы сортируются по убыванию длительности,
при равенстве — по времени предыдущей свечи; дефекты — по времени открытия.
Флаги `pauses_truncated` и `invalid_samples_truncated` показывают усечение.
Счётчики и максимальная длительность охватывают весь диапазон, даже при лимите 0.

Анализ выполняется SQL-агрегатами и оконной функцией `LAG` рядом с базой.
В Python и HTTP-ответ не выгружается свечной OHLCV-ряд. Первое вычисление всё
равно требует чтения истории в БД; это не обещание постоянной стоимости.
Ограниченный LRU-кэш хранит до 64 результатов на экземпляр хранилища по
инструменту, интервалу, границам, генерации, прогреву и лимиту примеров.
Новая генерация получает другой ключ; постоянного манифеста и фонового
пересчёта при импорте пока нет.

## Ошибки

- Неверный JSON/структура, неподдерживаемые тип или интервал, отрицательный
  прогрев, превышение лимитов или дополнительные поля: HTTP 400 `VALIDATION_ERROR`.
- Неизвестный/истёкший `snapshot`: HTTP 400 `INVALID_SNAPSHOT`.
- Неизвестный инструмент, неоднозначная идентификация, неправильные даты/порядок
  границ: ошибка соответствующего результата при HTTP 200, `status=not_ready`.
  Остальные пары продолжают проверяться. `warmup=null` означает, что анализ
  этой пары не выполнен; нулевые счётчики тогда не являются результатом проверки.
- Ошибка БД или исполнения: HTTP 500 `INTERNAL_ERROR`, не положительный вердикт.

Отчёт не меняет торговые решения робота автоматически. Подключение его к роботу,
перенос оставшихся проверок границ и выпуск обновлённой сборки — отдельные шаги.

## Проверка реализации

```bash
.venv/bin/python -m pytest tests/unit/test_data_quality.py tests/unit/test_instrument_api.py
```

Тесты проверяют паузы, усечение примеров, дефекты, закрытый прогрев, месяцы,
независимость таймфреймов, сохранение старого снимка после исправления свечей,
ошибки батча, Swagger и неизменность UID `/coverage`.
