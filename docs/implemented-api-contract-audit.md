# Неточности реализованного API: реестр для согласованной миграции

Дата анализа: 2026-10-10.

Статус: **исторический аудит прежнего UID-контракта**. Публичная поверхность
эмулятора заменена контрактом type+ticker; My_roBot ещё использует прежний
контракт и требует отдельной миграции.

После этого аудита согласован целевой ресурс инструмента по типу и тикеру:
[`instrument-resource-api-design.md`](instrument-resource-api-design.md).
`openapi.yaml` отражает реализованные формы чтения. Ниже сохранён аудит
удалённого UID-контракта; его проблемы и ссылки на код остаются основанием
для миграции робота.

## 1. Область анализа и правило дальнейшей работы

Проверены операции прежней реализации:

- `GET /health`;
- `GET /api/v1/candles`, `POST /api/v1/candles/batch`;
- `GET /api/v1/coverage`;
- `GET /api/v1/instruments`, `GET /api/v1/instruments/{instrument_id}`;
- `GET /api/v1/market-import/status`, `POST /api/v1/market-import/sync`;
- `GET /api/v1/market-import/intervals`, `/conflicts`, `/missing-instruments`.

Источники: `docs/openapi.yaml`, `src/api/routes/`, `src/api/schemas.py`,
`src/api/errors.py`, `src/storage/{candle_repository,instrument_repository,
import_repository,database}.py`, `src/market_import/{service,client}.py`.

Дальнейшая работа включает миграцию My_roBot к type+ticker и проверку
потребителей удалённых UID-маршрутов.
Отсутствие найденного вызова в одном клиентском файле не доказывает отсутствие
интеграции. Действующие операции не переводятся в эту категорию без проверки
всех потребителей. Настоящий документ — отдельный бэклог общей миграции.

Ниже различаются **фактическое расхождение** реализации и спецификации и
**проектный долг** публичного интерфейса. Не всякое совпадение имени поля с
колонкой БД является утечкой: идентификаторы инструментов, OHLCV, результат
синхронизации и счётчики имеют самостоятельный смысл для потребителя.

## 2. Свечи и покрытие

### E01. `total`: описание схемы расходится с условием вычисления

**Расхождение.** В схеме `CandlesResponse` сказано «всего свечей в диапазоне;
null, если диапазон не ограничен». Часть документации подразумевает обе
границы. `get_candles` и `_batch_item` вычисляют `total`, если задана **хотя бы
одна** из `from`/`to`; при отсутствии обеих возвращают `null`.

Будущая правка: единое точное описание для одиночного и батчевого чтения.

### E02. Курсор чтения связан с представлением времени в хранилище

**Проектный долг.** `next_cursor` — текст `ts` последней свечи.
`CandleRepository.query_page` сравнивает переданный `cursor` с текстовым `ts`
без разбора и нормализации. Произвольное значение, ISO-время с `T` или иная
таймзона могут дать другую выборку, чем ожидает клиент. Передача курсора ровно
из предыдущего ответа работает по действующему контракту.

Будущая правка: либо зафиксировать и валидировать временной курсор, либо сделать
продолжение непрозрачным для клиента. Изменение требует миграции клиента.

### E03. Снимок чтения раскрыт как номер внутренней генерации

**Проектный долг.** `snapshot_generation` прямо используется как граница
`canonical_candle_history.generation`. Проверяется только неотрицательность;
не определены публичные правила для номера больше текущей генерации,
другой базы, срока действия и сохранности снимка после миграции.
Снимок фиксирует свечи, но не каталог инструментов: `coverage` проверяет
наличие карточки в текущем каталоге.

Будущая правка: определить клиентский контракт снимка и его область действия.
Не удалять возможность консистентного чтения: она полезна интеграции.

### E04. Несогласованные ошибки отрицательного `snapshot_generation`

**Расхождение семантики кодов.** `candles` и батч возвращают
`INVALID_PAGE_LIMIT`, а `coverage` — `INVALID_TIME_RANGE`. Ни один код не
описывает ошибку идентификатора снимка.

Источник: `get_candles`, `_batch_item`, `get_coverage`.
Будущая правка: согласовать отдельный код или общий код валидации.

### E05. `slots` не доказывает полноту истории

**Проектный долг и неточность описания.** `interval_slots` считает временные
позиции без торгового календаря. Из `count < slots` нельзя заключить, что есть
пропуски; утверждение «count всегда меньше slots» также неверно для полностью
заполненного диапазона. Для месячного интервала оценка отсутствует.

Будущая правка: отказаться от `slots` в клиентской проверке полноты либо
строго обозначить его ограниченную математическую семантику.

### E06. Границы и количество свечей ошибочно подаются как гарантия покрытия

**Проектный долг.** `coverage` выполняет `MIN/MAX/COUNT`, но не обнаруживает
срединные пробелы и не учитывает причины отсутствия торгов. Описание обещает
помочь убедиться, что глубины достаточно, без ясной границы этой гарантии.

Будущая правка: различать имеющийся диапазон и подтверждённую полноту данных;
не вводить `complete=true` только на основании крайних свечей.

### E07. Неодинаковый ответ для неизвестного инструмента

**Неоднородность контракта.** `candles` и батч могут вернуть пустую выборку
для неизвестного UID; `coverage` и карточка инструмента возвращают 404 либо
503, если ожидаются метаданные. Клиент не всегда может отличить «нет свечей»
от «ошибка идентификатора» одинаковым способом.

Будущая правка: согласовать ожидаемую семантику; не менять ответы без миграции.

### E08. Граница изоляции ошибок в батче описана недостаточно точно

**Неточность описания.** Неверный поддерживаемый интервал, порядок границ и
числовой лимит обрабатываются поэлементно. Но некорректный тип поля или
неразбираемая дата отклоняются Pydantic при разборе всего запроса.
Поэтому не любая ошибка одного подзапроса остаётся внутри `results[i].error`.

Будущая правка: явно перечислить ошибки всего батча и отдельного элемента.

### E09. Точность времени и равные границы не определены единообразно

**Неточность контракта.** Запросы допускают доли секунды, но `fmt` и
`_normalize_ts` приводят границы к целым секундам. Это может менять смысл
включительности. Несмотря на обозначение `[from, to]`, запрос `from == to`
отклоняется (`from >= to`).

Будущая правка: определить поддерживаемую точность и допустимость диапазона
одной точки; согласовать валидацию, хранение и документацию.

## 3. Инструменты

### E10. `X-Total-Count` не учитывает все фильтры

**Подтверждённая ошибка.** `find_instruments` фильтрует список по `ticker`,
`figi`, `instrument_type`, но вызывает `count` только с `instrument_type`.
Заголовок может содержать число инструментов всего типа вместо числа
результатов поиска. Swagger обещает число подходящих записей.

Источник: `src/api/routes/instruments.py::find_instruments`,
`InstrumentRepository.count`.
Будущая правка: одинаковые фильтры для выборки и подсчёта.

### E11. Неверная рекомендация по определению полной страницы каталога

**Неточность описания.** В автоматически генерируемой документации сказано:
«меньше 5000 записей — ответ точно полный». Это неверно, если клиент передал
меньший `limit` или ненулевой `offset`. Увеличить `limit` выше 5000 также нельзя.

Будущая правка: описать завершение пагинации относительно фактического лимита
и корректного общего количества; проверить обход страниц в интеграции.

### E12. Валидация `instrument_type` расходится со статической схемой

**Расхождение.** В `docs/openapi.yaml` фильтр ограничен enum. В реализованном
маршруте это произвольная строка, передаваемая в SQL-фильтр; неизвестный тип
может дать пустой список вместо ошибки валидации.

Будущая правка: выбрать и согласовать поведение неизвестного типа.

### E13. Неоднозначные единицы ГО и стоимости шага

**Расхождение описаний.** `InstrumentResponse` описывает ГО как «в долях цены»,
а маршрут получения карточки — как сумму в рублях. Отсутствуют единые явные
единицы для разных видов инструментов и валют. Число нельзя интерпретировать
одинаково только по названию поля.

Будущая правка: согласовать единицы с источником и расчётами робота. До этого
не переименовывать и не преобразовывать финансовые поля самостоятельно.

**Решение (seed по семействам).** Робот отказывает автопрогону контрактной
цепочки, если у контракта нет `price_step`/`step_cost`/`go_buy`/`go_sell`.
Tinkoff для погасшего контракта (например, NG-1.25/`NGF5`) отдаёт эти поля
нулями, а ISS Мосбиржи инструмент удаляет. Поэтому отсутствующие значения
дозаполняются явной seed-таблицей по семействам (`base_code`) в
[`src/storage/futures_financials.py`](../src/storage/futures_financials.py):
шаг цены — из спецификации MOEX, стоимость шага и ГО — значения семейства в
рублях (единицы как у живых контрактов). Заполняются только `NULL`-поля, а
источник сохраняется в `instruments.fin_source`. Публичные модели инструмента
поле `fin_source` не отдают.

### E14. Обязательность полей и ошибки описаны разными спецификациями по-разному

**Расхождение документации.** Статическая схема `Instrument` требует только
три поля; Pydantic делает ряд nullable-полей обязательными в ответе.
Маршруты карточки и `coverage` могут вернуть `INSTRUMENT_METADATA_PENDING`
(503), но это не описано в их декораторах. Статическая спецификация 503 содержит.

Будущая правка: сверить `required`, `nullable`, все ошибки и примеры между
`docs/openapi.yaml` и генерируемым `/openapi.json`.

## 4. Импорт market-import

### E15. Ответы напрямую связаны с SQL-моделью

**Подтверждённая утечка модели хранения.** `source_state` делает `SELECT *`
из `import_sources` и возвращает `dict(row)`. Остальные методы возвращают
словари выбранных строк; маршруты не преобразуют их в публичные модели.
Добавление колонки или изменение SQL может неявно изменить API.

Технические поля: `after_id`, `min_after_id`, `max_change_id`,
`acknowledged_through`, `target_change_id`, `change_id`.
`producer_id`, источник и версия могут иметь диагностическую ценность,
но их смысл должен определяться контрактом, а не структурой таблицы.

Будущая правка: отдельные схемы ответов и явное отображение внутреннего
состояния в стабильную публичную диагностику.

### E16. Состояния импорта в Swagger не соответствуют коду

**Расхождение.** Для источника описаны `ready | pending | blocked | error`,
а код использует `ready | incomplete | blocked | error`.
Для интервалов описаны `ready | pending | unresolved`, а импорт принимает
`scheduled_closed | confirmed_no_trade | pending | unresolved`.

Будущая правка: согласовать состояния и их смысл. «Биржа закрыта» и «торгов
не было» — полезные сведения о данных, а не автоматически лишние внутренние поля.

### E17. Типы цен конфликтующих свечей не соответствуют схеме

**Подтверждённое расхождение.** `imported_*` объявлены как JSON numbers.
Но цены `imported_candle_versions` хранятся в TEXT, а `conflicts` отдаёт их
напрямую: в JSON это десятичные строки. `broker_*` поступают из REAL-колонок.

Будущая правка: определить единый формат с учётом точности цен и существующего
клиента. Вложенные объекты двух свечей лучше отделяют публичную модель от SQL JOIN,
но такая смена формы тоже требует миграции.

### E18. Формат времени импорта не соответствует общему правилу Swagger

**Расхождение.** Общая часть спецификации обещает наивный UTC с единственным
исключением для экспирации. Импорт возвращает ISO-время со смещением/`Z`,
часто с долями секунды (`last_success_at`, `open_time_utc`, `observed_at`,
`last_attempt_at`).

Будущая правка: либо явно определить исключения, либо согласованно нормализовать
время. Не менять формат изолированно от потребителя.

### E19. Ошибки market-import нарушают объявленную общую форму

**Подтверждённое расхождение.** Маршруты выбрасывают
`HTTPException(detail=str(exc))`; обработчик `HTTPException` не переопределён.
Ответ имеет форму `{"detail": "..."}`, а не `{"error": {"code", "message"}}`.
Текст включает сведения внутренних ошибок курсора и источника; стабильного
машинного кода не хватает. Источниковые 401/409/410 также отображаются в HTTP
эмулятора неодинаково.

Будущая правка: стабильные ошибки с явной семантикой и согласованная миграция
обработки ошибок роботом.

### E20. `last_sync` не имеет определённой схемы

**Проектный долг.** Схема допускает произвольный объект, маршруты не имеют
типизированных response_model. Реальный `last_sync` содержит
`producer_id`, `target_change_id`, `snapshot_generation`; это краткая сводка,
а не полный ответ `sync` и не `ImportSource`.

Будущая правка: отдельная схема этой сводки и описанная семантика `null`.

### E21. Диагностика отсутствующих карточек повторяет внутреннюю очередь

**Проектный долг.** `missing-instruments` выдаёт UID, `last_attempt_at`,
`last_error` без преобразования. UID полезен, но тип ошибки и обещания по
повторной попытке не определены; клиенту предлагается разбирать сырой текст.

Будущая правка: стабильные причины недоступности метаданных и определённая
диагностическая информация о повторных попытках.

## 5. Сквозные неточности

### E22. Два источника OpenAPI описывают API неодинаково

`/openapi.json` и интерактивная документация теперь обслуживаются из
`docs/openapi.yaml`; это один публичный источник контракта. Старые замечания о
расхождении с автоматически сгенерированными схемами относятся к удалённой
поверхности.

Будущая правка: расширять автоматическую сверку статической спецификации и
ответов работающего сервера.

### E23. Сообщения валидации зависят от представления Pydantic

Обработчик ошибки формирует `message` из `loc` и `msg` первой ошибки. Это не утечка
БД, но зависимость публичного текста от библиотеки. Клиент должен опираться на код,
а не разбирать этот текст. Если нужны ошибки отдельных полей, требуется отдельная
стабильная схема.

Для `GET /health` самостоятельных неточностей в проверенном контракте не найдено.
Поля OHLCV, UID/FIGI, интервалы, свойства инструментов и полезные агрегаты сами по
себе не считаются утечкой внутренней модели.

## 6. Состав будущей общей миграции

1. Подтвердить всех потребителей каждой implemented-операции и зафиксировать
   действующий контракт интеграционными примерами/тестами.
2. Согласовать целевую модель ошибок, времени, пагинации, снимков и диагностики.
3. Выбрать механизм совместимости: версия API либо переходный адаптер; решение
   пока не принято.
4. Внести согласованные изменения в эмулятор, клиент робота и обе спецификации.
5. Проверить исторический прогон, консистентное чтение, обработку ошибок,
   финансовые единицы и импорт в связке двух приложений.

Целевая спецификация чтения уже согласована как инструмент с подчинёнными
свечами/покрытием. Ввод этой формы в работающий API требует миграции из списка
выше; правки Swagger сами по себе её не выполняют. Остальная диагностика импорта
пока сохраняет действующий контракт и отдельный бэклог замечаний.
