# Инструмент как главный ресурс API

Статус: **контракт реализован в эмуляторе; миграция клиента робота впереди**.
Контракт в [openapi.yaml](openapi.yaml) помечен `x-status: implemented`.
Сервер обслуживает новую публичную форму запроса и ответа. До миграции My_roBot
сохранены UID-маршруты, совместимые с Tinkoff API; они не расширяют новый контракт.

## 1. Ответственности ресурсов

Главная сущность чтения — **инструмент**, публичный ключ —
`instrument_type + ticker`. Его представления:
- карточка — сведения об инструменте;
- `candles` — сами сохранённые свечи;
- `coverage` — сведения о доступности сохранённой истории без массива свечей.

Свечи и покрытие объединены под инструментом и одним тегом `instruments`,
но остаются отдельными операциями: статистику можно получить дешёво, без
выгрузки данных. Батч находится на уровне коллекции, потому что касается
нескольких инструментов. `downloads` остаётся отдельным ресурсом процесса:
он может загружать один инструмент или всю серию фьючерсов.

## 2. Идентификация

Во всех целевых пользовательских запросах и результатах используются тип и
тикер. UID Tinkoff, FIGI и внутренние ключи БД клиент не передаёт и не получает.
Сервис самостоятельно разрешает публичный ключ и связывает его со свечами.

Список инструментов поддерживает фильтры `ticker` и `instrument_type`.
Карточка, свечи и покрытие получают оба значения из пути. В батче они находятся
в каждом элементе. В загрузке конкретного инструмента это `target`;
для серии остаётся `instrument_type=future + base_asset`.

Каталог чтения поддерживает `share`, `future`, `etf`, `currency`.
Загрузка поддерживает `share` и `future`.
Тикер передаётся в канонической форме каталога, без пробелов, с URL-кодированием
сегмента пути. Неизвестная строка не интерпретируется автоматически как UID/FIGI.

### Однозначность

Тикер не считается глобально уникальным. В пределах поддерживаемого каталога
сервис должен обеспечивать однозначность пары типа и тикера. При конфликте —
409 `AMBIGUOUS_INSTRUMENT`, без произвольного выбора записи и без предложения
пользователю перейти на UID. Разрешение площадки/класса — задача конфигурации
и каталога сервиса. Исторические переименования и повторное использование
тикеров нельзя обрабатывать склеиванием разных инструментов: нужны проверенные
соответствия/алиасы либо явный конфликт. Внутренние стабильные UID сохраняются.

## 3. Операции

| Операция | Ответственность |
| --- | --- |
| `GET /api/v1/instruments` | Каталог и поиск по типу и тикеру |
| `GET /api/v1/instruments/{instrument_type}/{ticker}` | Карточка инструмента |
| `GET /api/v1/instruments/{instrument_type}/{ticker}/candles` | Свечи инструмента |
| `GET /api/v1/instruments/{instrument_type}/{ticker}/coverage` | Доступность сохранённой истории |
| `POST /api/v1/instruments/candles/batch` | Свечи нескольких инструментов |

Все пять форм описаны в OpenAPI как implemented. Deprecated-маршруты
`/api/v1/candles`, `/api/v1/candles/batch`, `/api/v1/coverage` и карточки по
`/{instrument_id}` в целевой спецификации нет. Это изменение документации
целевого API сохранены только как временная compatibility-поверхность.

## 4. Каталог и карточка

Каталог возвращает объект `InstrumentList`:
`instruments`, `count`, `total`, `snapshot`, `next_cursor`, `_links`.
`total` учитывает все фильтры. Пагинация идёт через `_links.next`, без offset.

Карточка `Instrument` содержит тип, тикер, полезные бизнес-метаданные и ссылки
`self`, `candles`, `coverage`. UID/FIGI не публикуются. Финансовые поля и единицы
должны быть сверены с расчётами робота при общей миграции; сохранение внутреннего
UID не зависит от его отсутствия в HTTP-представлении.

## 5. Свечи

Запрос поддерживает `interval`, необязательные `from`/`to`, `limit`,
непрозрачное продолжение `cursor` и необязательный `snapshot`.
UID/FIGI не являются query-параметрами. Ответ `CandlesResponse` содержит тип,
тикер, интервал, нормализованный диапазон, снимок, счётчики, свечи и `_links`.

Поля свечи остаются `datetime, open, high, low, close, volume`; порядок по времени
возрастающий. `total` вычисляется при хотя бы одной границе, иначе null.
Найденный инструмент без свечей — 200 с пустым массивом, неизвестный — 404.

Для целевого чтения и загрузки дата без времени в from означает начало дня UTC,
в to — конец дня (23:59:59). Timestamp допускает целые секунды и смещение,
которое переводится в UTC. Корректность календаря и `from < to` проверяет сервис.

## 6. Покрытие

Покрытие нужно для статистики, предзапусковой проверки и объяснения отсутствия
данных. Оно не выставляет внутренние настройки планировщика.

`CoverageResponse` содержит:
- `requested_range` — нормализованные ограничения запроса;
- `available_range` — крайние имеющиеся свечи в диапазоне, либо null;
- `count` — количество сохранённых свечей;
- `status`: `complete`, `partial`, `missing`, `unknown`;
- необязательную понятную `reason`, снимок и ссылки на свечи.

`complete` требует подтверждения исполнения/источника. MIN/MAX/COUNT недостаточно.
При отсутствии доказательства — unknown. Подтверждённое отсутствие торгов может
дать complete и count=0. Поле `slots` не публикуется.

## 7. Батч

`CandleBatchRequest.requests` содержит от 1 до 256 подзапросов с типом, тикером,
интервалом и диапазоном. Общий `snapshot` задаётся на уровне батча.
Результаты соответствуют порядку requests, каждый содержит тип/тикер, свечи,
счётчики, ошибку или ссылки для продолжения. Всё читается из одного снимка.

Неверный тип JSON-поля, отсутствующее обязательное поле и превышение количества
подзапросов отклоняют весь батч. Неверное значение типа, интервала, строка даты,
порядок границ, неизвестный/неоднозначный тикер и ошибка продолжения возвращаются
в соответствующем `results[i].error`; остальные запросы выполняются.
Непригодный общий snapshot — ошибка всего батча.

## 8. Снимки и пагинация

Клиент следует `_links.next`, не вычисляя курсор из времени, UID или номера строки.
Ссылка сохраняет фильтры, инструмент, интервал, границы, лимит и снимок.

Без snapshot сервис создаёт непрозрачный снимок и возвращает его в ответе/ссылках.
Один snapshot применим к каталогу, карточкам, свечам, покрытию и батчу: фиксирует
данные и соответствие публичных тикеров внутренним инструментам. Он не превращает
UID или числовую генерацию БД в клиентский параметр.

Снимок должен сохранять консистентность на протяжении исторического прогона.
Перезапуск при сохранённых данных не должен менять содержимое того же снимка;
при отсутствии требуемого набора данных/непригодном токене — `INVALID_SNAPSHOT`.
Внутреннюю реализацию и хранение снимков предстоит адаптировать.

Действующий `market-import/sync` остаётся legacy-интеграцией и возвращает числовой
snapshot_generation. Его нельзя передавать как snapshot в новый контракт.
Адаптация связки импорта и консистентного чтения входит в общую миграцию робота.

## 9. Ошибки

Форма — `{error: {code, message}}` для целевого чтения. Основные HTTP-коды:
- 400 — неверные параметры, интервал, границы, продолжение или снимок;
- 404 — инструмент не найден;
- 409 — публичный ключ неоднозначен;
- 503 — метаданные временно недоступны.

Текст не является машинным протоколом. Ошибки батча используют тот же объект
code/message внутри элемента. Неподдерживаемые способы идентификации не
добавляются как скрытые альтернативы тикеру.

## 10. Согласованная миграция

| Действующий интерфейс | Целевой интерфейс |
| --- | --- |
| GET /candles?instrument_id=... | GET /instruments/{instrument_type}/{ticker}/candles |
| POST /candles/batch, UID в элементах | POST /instruments/candles/batch, тип и тикер в элементах |
| GET /coverage?instrument_id=... | GET /instruments/{instrument_type}/{ticker}/coverage |
| GET /instruments, фильтр FIGI, ответ-массив | GET /instruments, тип/тикер, объект InstrumentList |
| GET /instruments/{instrument_id} | GET /instruments/{instrument_type}/{ticker} |
| Числовой snapshot_generation | Непрозрачный snapshot, общий для чтения данных и каталога |

Все маршруты таблицы имеют префикс `/api/v1`. Перед введением нового контракта
требуется согласованно обновить сервер, адаптер и чтение данных роботом,
контрактные тесты, исторический прогон и документацию подключения.
UID остаётся внутри репозиториев и связей БД. Механизм перехода/версии API —
отдельное решение реализации; здесь зафиксирована целевая форма маршрутов.
