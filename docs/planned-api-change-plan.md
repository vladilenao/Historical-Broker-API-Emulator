## 1. Граница работ

Согласована новая модель публичного чтения: инструмент по типу и тикеру,
подчинённые свечи и покрытие, батч на коллекции инструментов. Она отражается
в Swagger как implemented, включая новую форму уже существующего GET /instruments.
Сервер уже использует эту поверхность; до миграции робота сохраняется
Tinkoff-совместимость UID.

Health и существующая диагностика market-import остаются implemented.
Их текущие технические идентификаторы/генерации относятся к legacy-интеграции;
они не вводятся как альтернативные параметры нового пользовательского API.

## 2. Уже учтено в проектируемой спецификации

1. **Акции и фьючерсы поддерживаются явно.** `instrument_type` остаётся
   обязательным: `share` или `future`. Это бизнес-атрибут, а не утечка модели.
   Поддержка ETF и валют в новой загрузке пока не объявляется.
2. **Один API загрузки.** Акция и конкретный фьючерс выбираются по `ticker`
   и типу, серия фьючерсов — по `base_asset`. Для `share` базовый
   актив недопустим; null, пустая/пробельная строка и несколько способов выбора
   одновременно отклоняются. UID/FIGI не являются публичными параметрами.
3. **Окна различаются по бизнес-смыслу.** Акция — запрошенный период.
   Фьючерсы — полная жизнь выбранных по пересечению контрактов. Фактическое
   окно по каждому интервалу видно в результатах.
4. **Подготовка автоматическая.** Клиенту не нужно синхронизировать каталог
   перед созданием загрузки. Пустой кэш и отсутствие подходящего инструмента
   после разрешения цели — разные ситуации.
5. **Внутренние политики убраны.** В новом запросе нет `kind`, `slice_policy`,
   `options.mode`; в ответах нет `job_id` и `seq`. По умолчанию догружается
   отсутствующее; исполнитель и алгоритм планирования скрыты внутри сервиса.
6. **Публичные названия обобщены.** `ticker` вместо `contract_ticker`,
   `instruments` вместо `contracts`. Общий предпросмотр, результат и ошибка
   используют единицу «инструмент × интервал».
7. **Продолжение страниц не вычисляется клиентом.** Новый API передаёт
   непрозрачный `next_cursor` и ссылку `_links.next`. Клиент следует ссылке
   или копирует значение, не знает о сортировочном ключе и номере строки.
8. **Дата окончания в новом запросе включает весь указанный день UTC.**
   Эта семантика едина для целевого чтения и загрузки; текущий код мигрирует
   согласованно с потребителем.
9. **Главный ресурс чтения — инструмент.** Карточка, свечи и покрытие
   адресуются по типу и тикеру; батч находится на коллекции. Все пять форм
   чтения входят в тег instruments, отдельные теги candles/coverage убраны.

Эти пункты отражены в YAML, дизайн-документе и HTTP-реализации downloads.

## 3. Согласованный состав контракта и задач реализации

### P01. Упростить поверхность каталога и общего предпросмотра

**Перестройка проектируемых маршрутов выполнена в OpenAPI.**

Общий каталог instruments сохраняется как основной ресурс, но его целевая
публичная форма переходит на тип и тикер. Это согласованное изменение
подключённого контракта, а не введение второго каталога.

Принятый состав:
- общие карточки читать через `GET /api/v1/instruments/{instrument_type}/{ticker}`;
- не вводить второй общий каталог под другим именем;
- planned `GET /futures` и `GET /futures/{id}` удалены из нового публичного набора;
- необходимые для выбора окон сведения показывать в общем предпросмотре
  загрузки, без обязанности клиента разбирать поля SDK;
- planned `POST /futures/selection` заменён на
  `POST /api/v1/history/downloads/selection` с тем же запросом, что у создания
  загрузки: `target`, `range`, `intervals`;
- синхронизация карточек выполняется внутри разрешения цели. Planned
  `/futures/sync` удалён из публичного набора; отдельная операция обслуживания
  каталога в текущий контракт не входит.

Новая форма чтения реализована; P10–P11 продолжаются в части миграции My_roBot.

### P02. Общий результат предпросмотра

Предпросмотр должен отвечать на вопросы потребителя:
- какие инструменты будут загружены;
- какие интервалы и фактические окна выбраны;
- где данные уже доступны и где потребуется загрузка;
- почему инструмент не попал в выборку или период недоступен.

Для акции и фьючерса используется единая модель «инструмент × интервал».
Технические поля первой минутной/дневной свечи, стратегия чанкинга и политики
обработки неполного покрытия клиенту для составления запроса не нужны.

Предпросмотр не создаёт загрузку и не скачивает свечи, но может обновлять
метаданные. Поэтому он не объявляется полностью read-only.

Ответ `DownloadSelectionResponse` содержит полный массив `items` с `window`,
`availability`, `coverage`, `action` и необязательной причиной. `availability`
описывает данные поставщика (`available`, `partial`, `unavailable`, `unknown`),
`coverage` — наличие требуемых данных (`complete`, `partial`, `missing`, `unknown`).
`action` показывает ожидаемый результат (`download`, `skip`, `unavailable`),
но не служит настройкой клиентского алгоритма. Исключённые инструменты —
в `excluded` с причиной, без технических полей SDK.

Неизвестная доступность проверяется во время исполнения; предпросмотр не
обещает заранее доказать полноту без сведений источника. Ограничение глубины
показывается как `HISTORY_DEPTH_LIMIT`; отсутствие торгов — `NO_TRADES` или
`MARKET_CLOSED` при наличии подтверждения. Сводка отдельно считает уже
доступные, требующие загрузки и недоступные пункты.

### P03. Завершить правила разрешения цели и доступности периода

Правила контракта:
- публичный ключ — тип и тикер; однозначность в поддерживаемом каталоге
  обеспечивает сервис. Конфликт — `AMBIGUOUS_INSTRUMENT` без случайного выбора
  и без возврата к UID; требуется уточнение соответствий/конфигурации каталога;
- неизвестный инструмент после обращения к каталогу/поставщику —
  `INSTRUMENT_NOT_FOUND`, а не ошибка пустого локального кэша;
- полностью недоступный период — `PERIOD_NOT_AVAILABLE`, отсутствие подходящих
  контрактов серии — `NO_MATCHING_INSTRUMENTS`;
- при частичной доступности акция загружается в доступных границах, ограничение
  видно в `availability`; синтетические свечи не создаются;
- при недостаточных метаданных окно не вычисляется наугад: возвращается
  `METADATA_UNAVAILABLE`; исключённый контракт и причина видны в `excluded`;
- UID/FIGI используются только внутри сервиса; в запросах загрузки они
  отклоняются. Исторические переименования тикеров не склеивают разные инструменты.

Предпросмотр сообщает ошибки синхронно: 400 — неверный запрос, 404 — инструмент
не найден, 409 — неоднозначная цель/недоступный период/пустая выборка, 502 —
поставщик недоступен, 503 — метаданных недостаточно. Создание проверяет форму
запроса до принятия, а ошибки разрешения цели после 202 сохраняет в ресурсе
загрузки; они не меняют уже отправленный HTTP-ответ.

Не подменять отсутствие инструментов пустым локальным каталогом. Метаданные
и данные поставщика проверяет сервис, а не клиент.

### P04. Определить гарантию инкрементальности

Крайние свечи и их количество недостаточны, чтобы подтвердить полноту окна.
`coverage=complete` разрешён только при подтверждении исполнения требуемого
окна и сведений поставщика о торгах. При недоказанной полноте — `unknown`,
который не позволяет пропустить проверку. Торговые перерывы и отсутствие
сделок считаются допустимыми только при подтверждении календарём/источником.
Целевой публичный coverage под инструментом служит статистике и проверке
доступности данных; он не управляет планировщиком. Новый планировщик использует
внутренние репозитории и отвечает за собственный результат. Текущая реализация
старого coverage заменяется при миграции, а не самим изменением YAML.

Режимы `missing_only`, `range`, `repair` остаются внутренними. Если нужна отдельная
бизнес-операция повторной сверки, её смысл согласуется до добавления в API.
Повторный идентичный POST и повтор упавших пунктов — не то же самое, что
обновление уже успешно загруженных данных.

### P05. Завершить публичную модель результатов и ошибок

Модель результата определена в `DownloadItem`:
- инструмент публично идентифицируется по `instrument_type`, `ticker`;
  пункт — дополнительно по `interval` и `window`;
- `candles_received` — все полученные свечи за все попытки, включая повторную выдачу;
- `candles_added` — новые уникальные свечи, добавленные загрузкой за все попытки.
  Повтор и изменение цены существующей свечи не увеличивают этот счётчик;
- сводка и отчёт включают `items_cancelled`; `items_total` равен сумме статусов;
- дублирующего boolean `skipped` нет; пропуск описывает `status=skipped` и `reason`;
- при ошибке пункта `error` — объект `DownloadProblem`, а не сырой текст;
- ошибки отчёта содержат инструмент, интервал и окно; общая ошибка до построения
  плана находится в отдельном `error` ресурса и отчёта;
- ошибки HTTP имеют единый envelope `DownloadError` с `{error: {code, message}}`.

`attempt` — номер попытки; времена начала, завершения и длительность относятся
к текущей попытке, счётчики свечей — ко всей загрузке. После успешного retry
текущая ошибка пункта очищается; старые ошибки не остаются текущим результатом.

Идентификатор загрузки непрозрачен; состав хэша не становится обязанностью клиента.

### P06. Завершить пагинацию и гипермедиа

Во всех новых коллекциях клиент получает продолжение через `_links.next`.
Внутренние ключи сортировки, offset таблицы, seq и номера генераций не входят
в клиентский алгоритм. Следующая ссылка сохраняет фильтры и размер страницы.
Первая страница фиксирует состав выборки и порядок: новые записи не попадают
в продолжение этого просмотра. Статусы уже выбранных записей могут обновляться.
Новую выборку начинают с первой страницы. Непригодное продолжение — 400
`INVALID_CURSOR`. Это правило относится к журналу и коллекции результатов;
полный ответ предпросмотра в пагинации не нуждается.

В целевом чтении также используются _links.next и непрозрачный snapshot,
который фиксирует данные и каталог. Числовая генерация БД не передаётся клиентом.
Переход с текущей пагинации и snapshot_generation входит в P11.

### P07. Завершить жизненный цикл загрузки

Статусы: `pending`, `running`, `cancelling`, `completed`, `partial`, `failed`,
`cancelled`. Последние четыре терминальные. Действия сообщаются через `_links`:
- создание — 202 с `Location`; идентичный POST — 200 с тем же ресурсом,
  без новой попытки и без возобновления отменённой работы;
- cancel при pending/running — 202 и `cancelling`, затем `cancelled`;
  повтор при cancelling — 202, при cancelled — 200, прочие терминальные — 409;
- незавершённые отменённые пункты получают `cancelled`, завершённые сохраняются;
- retry при partial/failed/cancelled — 202, тот же `download_id`, attempt+1,
  новый статус pending; повторяются только failed/cancelled, либо разрешение
  цели, если план ещё не создан;
- при активной/успешной загрузке или отсутствии повторяемой работы retry — 409;
  конкурентный повтор не создаёт второй набор исполнения;
- после перезапуска незавершённое исполнение восстанавливается с прежним ID.

Фоновая работа и восстановление после перезапуска выполняются внутренними
Python-сервисами; HTTP-ресурсы jobs не возвращаются.

### P08. Адаптировать внутреннюю модель и диаграммы к акциям

Разделы 4 и 6 исходного дизайна пока сохраняют фьючерсный сценарий.
При следующем согласованном обновлении проверить:
- единицу результата «инструмент × интервал» и хранение окна акции;
- ссылки на инструмент, поля тикера и внутренние разновидности цели;
- сводки и отчёты для разных типов инструментов;
- фьючерсные метаданные как расширение, неприменимое к акциям;
- восстановление исполнения и согласованную миграцию данных и клиента робота.

Публичный `kind` для этого не нужен: тип и цель известны из запроса.

### P09. Проверить реализованный контракт

Проверки схем и сценариев:
- акция по тикеру, один фьючерс, серия фьючерсов;
- неверная комбинация типа и цели, отсутствие цели, две цели, null/пустая строка;
- даты и timestamps, включительность конечного дня;
- идемпотентность, пустой кэш, частичное наличие данных;
- недоступные данные, частичный сбой, отмена, повтор и перезапуск;
- продолжение страниц только по возвращённой ссылке;
- отсутствие внутренних политик, job_id и seq в запросах и ответах.
- тип и тикер во всех новых формах чтения и загрузки, отсутствие UID/FIGI;
- один тикер в разных типах, конфликт внутри типа, исторические алиасы;
- каталог с фильтрами и полным total, вложенные свечи/покрытие и батч;
- один непрозрачный снимок для каталога, карточек, свечей, покрытия и батча.

Операции прошли реализацию и контрактные проверки; их статус в OpenAPI —
implemented.

### P10. Инструмент как главный публичный ресурс чтения

Полная спецификация — в `instrument-resource-api-design.md` и OpenAPI:
- публичный ключ — instrument_type + ticker; UID/FIGI внутренние;
- GET /instruments — фильтры типа/тикера, объект InstrumentList, пагинация по ссылкам;
- GET /instruments/{instrument_type}/{ticker} — карточка и ссылки на данные;
- вложенные /candles и /coverage — чтение данных и статистика;
- POST /instruments/candles/batch — пары типа/тикера в каждом элементе;
- coverage не публикует slots и не выводит полноту из крайних свечей;
- необязательный snapshot — непрозрачная строка, общая для всех форм чтения;
- идентичная публичная пара используется в загрузках, результатах и ошибках.

Отдельных candles/coverage на корневом уровне и карточки по UID в целевом
Swagger больше нет. Однозначность пары и сохранность снимка обеспечиваются
сервисом, а не выбором внутреннего идентификатора потребителем.

### P11. Миграция существующей интеграции робота

Нужно согласованно изменить сервер и клиента робота:
- маршруты и передачу типов/тикеров вместо UID;
- каталог: массив/offset/FIGI → InstrumentList, фильтры типа/тикера, _links.next;
- получение карточки и переход к свечам/покрытию по подчинённым ссылкам;
- батчевое чтение и изоляцию ошибок;
- привязку снимка данных и каталога, замену передачи внутренних генераций;
- обработку неизвестной/неоднозначной пары и недоступных метаданных;
- контрактные тесты и исторический прогон в связке двух приложений.

Текущие запросы робота не предполагаются совместимыми с новой формой автоматически.
Механизм перехода и развёртывание выбираются перед реализацией. Стабильные
внутренние UID, таблицы и архив истории сохраняются.

## 4. Итоговый набор новых ресурсов в OpenAPI

| Операция | Ответственность |
| --- | --- |
| `GET /api/v1/` | Ссылки на доступные ресурсы |
| `GET /api/v1/instruments` | Каталог по типу и тикеру |
| `GET /api/v1/instruments/{instrument_type}/{ticker}` | Карточка инструмента |
| `GET /api/v1/instruments/{instrument_type}/{ticker}/candles` | Свечи инструмента |
| `GET /api/v1/instruments/{instrument_type}/{ticker}/coverage` | Доступность сохранённой истории |
| `POST /api/v1/instruments/candles/batch` | Свечи нескольких инструментов |
| `POST /api/v1/history/downloads/selection` | Общий предпросмотр загрузки акции или фьючерсов |
| `POST /api/v1/history/downloads` | Создать загрузку |
| `GET /api/v1/history/downloads` | Журнал загрузок |
| `GET /api/v1/history/downloads/{download_id}` | Статус и сводка |
| `GET /api/v1/history/downloads/{download_id}/items` | Результаты по инструментам и интервалам |
| `GET /api/v1/history/downloads/{download_id}/report` | Итоги и ошибки |
| `POST /api/v1/history/downloads/{download_id}/cancel` | Запросить отмену |
| `POST /api/v1/history/downloads/{download_id}/retry` | Повторить неуспешную/отменённую работу |

Все четырнадцать целевых операций перечислены с `x-status: implemented`.
Отдельных futures*, candles*, coverage и карточки по UID в целевой поверхности
нет. Шесть implemented-операций — health и диагностика market-import.
Новые формы чтения и загрузки реализованы. Клиент My_roBot пока использует
Tinkoff-совместимость UID и должен переключаться по
`robot-api-migration-spec.md`.
