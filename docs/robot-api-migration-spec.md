## 1. Задача и границы перехода

Исторический режим должен читать карточки, свечи и покрытие через публичный ключ
`instrument_type + ticker`. Эмулятор сам разрешает этот ключ в свой внутренний UID.
Робот не передаёт UID/FIGI в HTTP и не ожидает их в карточках целевого API.

Переход относится к источнику рыночных данных, его адаптеру и связанным вызовам.
Формат свечей для стратегий остаётся:

```python
["datetime", "open", "high", "low", "close", "volume"]
```

Для боевого источника Tinkoff реальные UID продолжают использоваться **внутри
SDK-адаптера**. Торговые заявки, учёт сделок и текущий экспорт рыночных данных
не переводятся автоматически на другой протокол из-за изменения исторического чтения.

`market-import` сохраняется в нынешнем виде. Его замечания E15–E21 из аудита
не являются частью этого задания на новый HTTP-клиент чтения.

## 2. Какие вызовы изменились

| Сейчас | Целевой вызов | Изменение клиента |
| --- | --- | --- |
| `GET /api/v1/instruments?instrument_type=share`, ответ-массив | `GET /api/v1/instruments?instrument_type=share`, ответ InstrumentList | Читать `instruments`, `total`, `snapshot`, `_links.next` |
| `GET /api/v1/instruments/{instrument_id}` | `GET /api/v1/instruments/{instrument_type}/{ticker}` | Выбор по типу и тикеру, карточка без UID/FIGI |
| `GET /api/v1/candles?instrument_id=...` | `GET /api/v1/instruments/{instrument_type}/{ticker}/candles` | Тип и тикер в пути, снимок и продолжение по ссылке |
| `POST /api/v1/candles/batch`, UID в элементах | `POST /api/v1/instruments/candles/batch` | Тип/тикер в каждом элементе, общий снимок |
| `GET /api/v1/coverage?instrument_id=...` | `GET /api/v1/instruments/{instrument_type}/{ticker}/coverage` | Границы, статус и причина; без slots |
| `GET /health` | `GET /health` | Проверка живости сохраняется |
| Начальная точка не используется | `GET /api/v1/` | Получить ссылки на каталог, батч и загрузки |

В проверенном `src/api/emulator_client.py` текущий робот действительно вызывает
health, одиночные candles, каталог и карточку по UID. Батч и coverage здесь
не вызываются; ниже описано их использование в целевом клиенте, а не утверждение
об уже работающих вызовах.

Базовый адрес задаётся существующим `HISTORICAL_API_URL` в `src/config.py`
(по умолчанию `http://127.0.0.1:8100`). Смена контракта не требует другого порта.
Сегменты типа/тикера кодируются для URL отдельно; тикер берётся из карточки
каталога, а не вычисляется из названия фьючерса или текста уведомления.

### Почему одной замены URL недостаточно

Сейчас `src/api/instruments.py` читает `inst.uid`, загрузчик возвращает
`(DataFrame, instrument_id)`, а кэш хранит `_uids` и передаёт их при дозагрузке.
Если только убрать UID из HTTP-карточки, эти вызовы получат пустые идентификаторы.
Кроме того, SDK-схемы инструментов больше не являются формой нового ответа сервера.

Поля с именем `instrument_id` в журнале/портфеле нельзя менять поиском с заменой:
например, `src/broker/journal_broker.py` передаёт `plan.instrument_id` как ticker.
Это может быть бизнес-ключ сделки, а не UID источника. Разделить эти значения
при аудите вызовов; не переписывать историю сделок только из-за смены HTTP-чтения.

## 4. Внутренний интерфейс рыночных данных

Рекомендуемый целевой подход — единый порт для двух источников, без ветвлений
«если эмулятор» в стратегии и сборке свечного кадра.

```python
# Эскиз будущего интерфейса робота, не существующий код.
@dataclass(frozen=True)
class InstrumentRef:
    instrument_type: str
    ticker: str

# Клиент источника:
list_instruments(instrument_type) -> list[InstrumentCard]
get_instrument(ref: InstrumentRef) -> InstrumentCard
get_all_candles(ref: InstrumentRef, *, from_, to, interval) -> Iterator[MarketCandle]
get_coverage(ref: InstrumentRef, *, from_, to, interval) -> Coverage
```

`InstrumentCard` содержит публичную пару, название, валюту, лот, ценовые параметры,
ГО и экспирацию, когда они доступны. `MarketCandle` содержит UTC-время и числовые
OHLCV. Это нормализованные модели внутри робота; новые модели/порт можно разместить
в предлагаемом `src/api/market_data.py` либо рядом с существующими моделями.

Для MarketCandle использовать datetime в naive UTC и числовые open/high/low/close,
целый volume. В порту interval — каноническая строка (`1h`, `1M` и т. д.);
SDK-адаптер переводит её в CandleInterval. Существующий TIMEFRAMES можно оставить
как таблицу валидации/SDK-маппинга, но loader не должен требовать SDK-тип свечи
или читать `.open.units/.nano` после HTTP-декодирования.

- HTTP-адаптер преобразует JSON в эти модели.
- SDK-адаптер преобразует объекты Tinkoff и самостоятельно разрешает UID.
- `ClientProvider` остаётся границей выбора источника и владения его ресурсами;
  доступ боевого приложения к остальным SDK-сервисам не заменяется HTTP-портом.
- Нельзя заполнять SDK `uid` тикером, пустой строкой или выдуманным UUID только
  ради сохранения старого кода. Это не настоящий идентификатор брокера.

Для уменьшения объёма изменения вызывающих функций допустимо сохранить арность
результата загрузчика как `(DataFrame, InstrumentRef)`: тогда preflight по-прежнему
может игнорировать второй результат. Тип и смысл второго результата должны быть
изменены явно в вызывающих функциях и тестах. UID-кэш в этом случае не нужен:
пара уже есть у инструмента, разрешение SDK кэширует сам боевой адаптер.

Ключи клиентских кэшей карточек — `(instrument_type, ticker, snapshot)`;
для кадров добавляется timeframe. В пределах одной сессии snapshot может храниться
в объекте-владельце кэша, а не повторяться в каждом ключе.

Сейчас `selector._deduplicate` и часть метаданных используют только ticker.
Их нужно проверить отдельно: источник различает одинаковый тикер в разных типах.
Если торговый контур пока использует только строковый ticker, на входе сессии
явно отклонять такой конфликт, а не молча удалять один инструмент или подменять
метаданные. Полный переход ключей журнала/торгового контура — отдельное изменение.

## 5. Запуск одной исторической сессии

1. Создать один `EmulatorClientProvider` на логический прогон.
2. Проверить `/health`, затем получить корневой ресурс `/api/v1/`.
3. Прочитать каталог по `_links.instruments`, получить строковый snapshot и
   сохранить его в общем объекте сессии.
4. Все следующие обращения к каталогу, карточкам, свечам и coverage выполнять
   с этим snapshot; батч передаёт его на верхнем уровне тела.
5. Выбрать инструменты, проверить прогрев/период, загрузить метаданные и запустить кэш.
6. Если preflight сдвинул начало и `_run_history` пересобирает часы/состояние,
   использовать тот же источник и снимок: проверяется тот же набор данных.
7. Завершить сессию вместе с прогоном. Новый самостоятельный прогон может получить
   новый снимок.

В текущем `run.py` провайдер создаётся внутри каждого прохода цикла `_run_history`.
Его нужно вынести к началу логического прогона. Каждый вызов `client_context()`
может создавать/закрывать транспортный клиент, но не должен обнулять общую сессию.
Первый запрос снимка выполняется до параллельного чтения, чтобы два контекста
не закрепили разные snapshot.

Для восстановления прогона сохранять opaque snapshot в технических метаданных
сессии и проверять его при повторном использовании state_dir. Состояние сделок
и кадры, рассчитанные на старом снимке, нельзя продолжать на незаметно созданном
новом. Если прежний снимок восстановить нельзя, требуется новый логический прогон
с отдельным/очищенным состоянием; формат хранения этих метаданных — задача реализации.

Корневые ссылки и форма первого ответа каталога являются проверкой контракта:
если сервер возвращает старый массив либо не поддерживает новую поверхность,
показать понятную ошибку несовместимости. `/health` сам по себе не доказывает
поддержку нового API. Не продолжать один прогон смесью старых и новых запросов.

## 6. Каталог и карточка: что читать из ответа

### 6.1. Каталог

```http
GET /api/v1/instruments?instrument_type=share&limit=5000
```

Пример ответа `InstrumentList`:

```json
{
  "count": 1,
  "total": 1,
  "snapshot": "opaque-read-snapshot",
  "next_cursor": null,
  "instruments": [
    {
      "instrument_type": "share",
      "ticker": "SBER",
      "name": "Сбербанк",
      "currency": "RUB",
      "lot": 10,
      "min_price_increment": 0.01,
      "expiration_date": null,
      "_links": {
        "self": {"href": "/api/v1/instruments/share/SBER?snapshot=opaque-read-snapshot"},
        "candles": {"href": "/api/v1/instruments/share/SBER/candles?interval=1d&snapshot=opaque-read-snapshot"},
        "coverage": {"href": "/api/v1/instruments/share/SBER/coverage?interval=1d&snapshot=opaque-read-snapshot"}
      }
    }
  ],
  "_links": {
    "self": {"href": "/api/v1/instruments?instrument_type=share&snapshot=opaque-read-snapshot"}
  }
}
```

Читать `payload["instruments"]`, а не итерировать весь payload как массив.
Обходить все `_links.next`; `limit=5000` не означает, что каталог всегда помещается
в одну страницу. `total` — число подходящих инструментов, count — текущая страница.
Для следующего типа передавать уже закреплённый snapshot, а не создавать новый.

### 6.2. Карточка и метаданные

```http
GET /api/v1/instruments/future/NG-1.26?snapshot=opaque-read-snapshot
```

Для источника использовать `instrument_type` и `ticker`. Отображаемый код
фьючерса из первого слова `name`/`short_name` не обязан совпадать с ticker.
`src/instruments/model.py` уже различает их: сохранить это правило именования.
Примеры NG-1.26 здесь иллюстративны; отправлять фактический ticker каталога.

В `fetch_active_futures` фильтровать экспирацию относительно виртуального
`market_now`, а не системного времени. Учитывать, что `name`, expiry и ценовые
поля могут отсутствовать или быть null; не вызывать `.lower()` на None и не
подставлять сегодняшнюю дату вместо неизвестной экспирации.

`load_futures_contracts` получает ГО и стоимость шага из карточки; отдельного
HTTP get_futures_margin по UID в новом API нет. Боевой адаптер при необходимости
делает соответствующий SDK-вызов внутри себя. Для акций сохранить расчёт
стоимости шага из price_step и lot, который уже используется роботом.

Отсутствующие метаданные не превращать в якобы подтверждённые нули/единицы.
Применять существующее поведение «нет метаданных контракта» явно. Единицы ГО
и стоимости шага ещё требуют согласования по E13 аудита: этот документ не
объявляет их исправленными и не предписывает новую формулу пересчёта.

## 7. Свечи, время и пагинация

### 7.1. Первый запрос

```http
GET /api/v1/instruments/share/SBER/candles?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&limit=1&snapshot=opaque-read-snapshot
```

Пример страницы `CandlesResponse`:

```json
{
  "instrument_type": "share",
  "ticker": "SBER",
  "interval": "1h",
  "range": {"from": "2025-01-01 10:00:00", "to": "2025-01-01 12:00:00"},
  "snapshot": "opaque-read-snapshot",
  "count": 1,
  "total": 2,
  "next_cursor": "opaque-next-page",
  "candles": [
    {"datetime": "2025-01-01 10:00:00", "open": 100.0, "high": 102.0, "low": 99.0, "close": 101.0, "volume": 500}
  ],
  "_links": {
    "self": {"href": "/api/v1/instruments/share/SBER/candles?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&limit=1&snapshot=opaque-read-snapshot"},
    "next": {"href": "/api/v1/instruments/share/SBER/candles?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&limit=1&snapshot=opaque-read-snapshot&cursor=opaque-next-page"}
  }
}
```

`_get` сейчас складывает base_url и path. Для href нужен корректный resolver,
например `urljoin(base_url + "/", href)`, который сохраняет query ссылки.
URL тикера строить через кодирование отдельного сегмента, а query — через urlencode.
На первом запросе можно заменить interval/from/to в ссылке карточки; в ссылке
продолжения параметры уже зафиксированы, их не пересобирать вручную.

### 7.2. Обход страниц

Алгоритм клиента:
1. Выполнить первый запрос с парой, интервалом, диапазоном и snapshot.
2. Проверить ожидаемый snapshot и соответствие возвращённой пары/интервала.
3. Добавить candles в результирующий срез.
4. Если `_links.next` есть, запросить **его href**; иначе закончить.
5. При известном total проверить полноту полученного числа строк; учитывать и total=0.

Не вычислять продолжение из максимального datetime, не прибавлять секунду,
не заменять snapshot. Повторяющийся href/продолжение, смена снимка или неверная
пара в ответе — ошибка протокола, а не повод молча обрезать срез.

### 7.3. Время и кадр стратегий

- from/to включительны; дата без времени означает начало дня для from и конец
  дня для to. Не превращать строку конечной даты в timestamp полуночи случайно.
- Для текущего виртуального момента отправлять явный timestamp, а не дату:
  дата расширила бы чтение до конца дня.
- Aware-время сначала перевести в UTC, затем сериализовать. Текущий to_naive
  удаляет зону без преобразования; его недостаточно для входа со смещением +03:00.
- Сохранить целые секунды, все девять интервалов и точный регистр `1M`.
- JSON-числа преобразовать в числовые OHLCV; datetime в итоговом DataFrame — naive UTC.
- Сортировка и объединение перекрывающихся окон в кэше сохраняются. Это не
  замена обхода всех страниц и не способ скрывать ошибку продолжения.
- `MarketDataCache._closed_only` и виртуальные часы по-прежнему ограничивают
  данные, доступные стратегии: зафиксированный набор истории сам по себе не
  предотвращает использование будущего бара.

## 8. Покрытие и preflight

```http
GET /api/v1/instruments/share/SBER/coverage?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&snapshot=opaque-read-snapshot
```

Пример `CoverageResponse`:

```json
{
  "instrument_type": "share",
  "ticker": "SBER",
  "interval": "1h",
  "requested_range": {"from": "2025-01-01 10:00:00", "to": "2025-01-01 12:00:00"},
  "available_range": {"from": "2025-01-01 10:00:00", "to": "2025-01-01 11:00:00"},
  "count": 2,
  "status": "unknown",
  "snapshot": "opaque-read-snapshot",
  "reason": {"code": "COVERAGE_NOT_CONFIRMED", "message": "Полнота истории пока не подтверждена."},
  "_links": {
    "self": {"href": "/api/v1/instruments/share/SBER/coverage?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&snapshot=opaque-read-snapshot"},
    "candles": {"href": "/api/v1/instruments/share/SBER/candles?interval=1h&from=2025-01-01T10:00:00&to=2025-01-01T12:00:00&snapshot=opaque-read-snapshot"}
  }
}
```

Coverage — быстрая диагностика, не единственное условие допуска стратегии:
- complete означает подтверждённость периода, но прогрев всё равно требует
  достаточного числа реальных баров;
- partial/missing — показать доступные границы и причину, затем применить
  действующие правила preflight;
- unknown не равен complete или missing: продолжить проверку реальных свечей
  и сообщить, что полнота источником не подтверждена;
- complete при count=0 может означать подтверждённое отсутствие торгов;
  не создавать искусственные бары для прогрева.

Сохранить проверки головы/хвоста, сдвига начала, прогрева и разрывов в
`src/history/preflight.py`. Все чтения, включая `_nearest_after/_nearest_before`
и сканирование непрерывности, используют один snapshot. Сведения coverage
могут дополнять отчёт, а не отменять проверки необходимых стратегии данных.

## 9. Батч: использование при добавлении оптимизации

Переход одиночного чтения не требует немедленно менять планировщик кэша на батчи.
Если клиент использует батч, отправлять публичные пары и общий snapshot:

```http
POST /api/v1/instruments/candles/batch
Content-Type: application/json
```

Пример тела `CandleBatchRequest`:

```json
{
  "snapshot": "opaque-read-snapshot",
  "requests": [
    {"instrument_type": "share", "ticker": "SBER", "interval": "1h", "from": "2025-01-01T10:00:00", "to": "2025-01-01T12:00:00"},
    {"instrument_type": "future", "ticker": "NG-1.26", "interval": "1d", "from": "2025-11-01", "to": "2025-12-31"}
  ]
}
```

Не более 256 элементов. `results[i]` относится именно к `requests[i]`;
не сопоставлять только по тикеру: интервалы и окна могут повторяться/различаться.
HTTP 200 не означает успех всех элементов. Проверить error каждого результата.
Продолжение конкретного успешного элемента — по его `_links.next`, уже через
GET вложенного candles; общий snapshot должен остаться тем же.

При ошибке всего запроса не принимать его как массив пустых свечей. Успешные
элементы можно сохранить в соответствующие кадры; ошибки других должны попасть
в отчёт и не переименовываться в «нет торгов».

## 10. market-import: сохранить действующий протокол

Направления обмена различаются:

```text
Исторический режим: My_roBot → эмулятор → карточки/свечи/покрытие
Импорт:            эмулятор → экспорт My_roBot → журнал рыночных данных
```

Клиент импортера в эмуляторе обращается к экспорту робота:
`/api/v1/market-data/source`, `/changes`, `/consumers/{consumer_id}/checkpoint`.
Эндпоинты `/api/v1/market-import/*` находятся на стороне эмулятора.
В проверенном HistoricalClient робота вызовов market-import нет.

Для этого перехода не менять экспортные поля instrument_uid, producer_id,
change_id, revision, подтверждения и их типы на основании нового ключа чтения.
В частности, нельзя записать ticker вместо реального UID в старое instrument_uid.

Если внешний этап подготовки уже вызывает market-import/sync, он сохраняет
нынешний контракт. Числовой snapshot_generation нельзя превращать в новый
snapshot с помощью str() или собственного кодирования. Новый снимок берётся
из первого целевого ответа чтения после подготовки данных.

Точное соответствие новому снимку старой границы журнала импорта сейчас не
определено: не обещать фиксацию ровно на returned snapshot_generation.
Известные ошибки E15–E21 и эта связка остаются отдельным бэклогом. Новый клиент
чтения не должен начинать разбирать legacy `detail` как свой error.code.

## 11. downloads: отдельная подготовка, если она нужна роботу

Обычный исторический цикл читает готовую историю. Не превращать каждый пустой
кадр или 404 в неявный запрос длительной загрузки. Если робот будет управлять
подготовкой данных, сделать отдельный этап **до фиксации снимка чтения**.

Последовательность:
1. При необходимости POST `/api/v1/history/downloads/selection` с целью/периодом/интервалами.
2. POST `/api/v1/history/downloads` с тем же телом.
3. Получить download_id и Location; при 200 использовать уже существующий ресурс.
4. По self/Location читать состояние и отчёт; применять доступные cancel/retry-ссылки.
5. После удовлетворительного результата начать новую сессию чтения и получить snapshot.

Пример тела `DownloadCreateRequest` для акции:

```json
{
  "target": {"instrument_type": "share", "ticker": "SBER"},
  "range": {"from": "2025-01-01", "to": "2025-12-31"},
  "intervals": ["1d", "1h"]
}
```

Для серии используется `future + base_asset`; каждый контракт — самостоятельный
инструмент, а не склеенный непрерывный ряд. Акция загружается за range,
фьючерсы — за полную жизнь выбранных контрактов. В запросе нет kind, mode,
slice_policy или job_id. Tinkoff-доступ для загрузки настраивается в эмуляторе;
чтение сохранённых данных историческим клиентом токена Tinkoff не требует.

completed — успешные/пропущенные пункты; partial требует просмотра errors,
failed не является готовностью истории; cancelled сохраняет скачанное.
Cancel возвращает 202/cancelling до окончательной остановки. Retry при допустимом
статусе повторяет failed/cancelled с тем же ID и новым attempt. Повторный POST
не возобновляет отменённую загрузку автоматически.

## 12. Ошибки и повторы

Сохранить в исключении клиента `status`, стабильный `code` и `message`.
Сетевой сбой/таймаут отличаются от корректного HTTP-ответа с ошибкой.

| Код / ситуация | Поведение исторического клиента |
| --- | --- |
| INSTRUMENT_NOT_FOUND / 404 | Показать пару; не искать через UID и не считать это пустой историей |
| AMBIGUOUS_INSTRUMENT / 409 | Сообщить о конфликте каталога; не выбирать первую запись |
| INSTRUMENT_METADATA_PENDING / 503 | Явная недоступность метаданных; допустим ограниченный повтор в том же снимке |
| INVALID_INTERVAL, INVALID_INSTRUMENT_TYPE, INVALID_TIME_RANGE, VALIDATION_ERROR | Исправление запроса, не бесконечный повтор |
| INVALID_CURSOR, INVALID_SNAPSHOT | Остановить текущую последовательность чтения; не продолжать с новым снимком поверх старых кадров |
| Сетевая ошибка, временный 5xx | Ограниченный повтор того же запроса/href с тем же snapshot |
| 200 и пустой candles | Данных в этом окне нет; применить логику preflight/разрывов |
| 200 батча с error элемента | Ошибка данного подзапроса, а не успех всего набора |

Сохранить защиту от повторяющегося продолжения и неполного количества строк.
При полном перезапуске после потери снимка очистить связанные кадры/метаданные
или восстановить именно прежний снимок; не смешивать две версии данных.
В боевом SDK-адаптере сохранить существующую обработку RESOURCE_EXHAUSTED и
ratelimit_reset. Исторический HTTP не должен зависеть от поиска этих слов в тексте.

## 13. Проверки и порядок реализации

### Порядок

1. Зафиксировать модели ссылки/карточки/свечи и интерфейс источника.
2. Реализовать HTTP-клиент и одну разделяемую сессию: root, каталог, карточка, ссылки.
3. Перевести инструменты/метаданные и loader/cache на публичную пару; адаптировать
   боевой источник внутри его SDK-границы.
4. Подключить один snapshot к selector, preflight, metadata и runtime; проверить
   повтор запуска после сдвига начала.
5. Проверить чтение, ошибки и исторический прогон; батч оптимизировать отдельно.
6. Переключить сервер и исторического клиента на согласованную форму. Механизм
   совместимости/версии выбирается при развёртывании, не предполагается автоматически.

### Файлы тестов робота

| Файл | Какие проверки обновить/добавить |
| --- | --- |
| `tests/unit/test_emulator_client.py` | Маршруты, envelope каталога, все страницы, href, snapshot, числа/даты, HTTP-ошибки; убрать обязательные UID в фикстурах |
| `tests/unit/api/test_instruments.py` | Новый порт, получение карточки/метаданных, отсутствие uid/get_futures_margin в HTTP-пути |
| `tests/unit/test_preflight.py` | Ответ `(DataFrame, InstrumentRef)`, единый снимок, unknown/пустые данные/ошибки источника |
| `tests/unit/test_cache_history.py` | Дозагрузка без `_uids`, закрытые бары и разрывы при прежних виртуальных часах |
| `tests/integration/test_historical_run.py` | Новый источник и каталог, повтор после сдвига, целостность снимка, отчёт прогона |

Приёмочные сценарии:
- акция и фьючерс по паре; разные типы с одинаковым тикером не смешиваются;
- неоднозначная пара и неизвестный инструмент дают различимые ошибки;
- каталог больше одной страницы, limit меньше total, корректные count/total;
- свечи больше одной страницы, total=0, повторяющийся href и смена snapshot;
- два клиентских контекста одного провайдера читают один снимок;
- метаданные и свечи привязаны к одному снимку, включая preflight/lookahead;
- вход со смещением +03:00 сохраняет момент UTC, date-only to включает весь день;
- виртуальный now передаётся как timestamp, будущие/незакрытые бары не уходят стратегиям;
- батч: порядок, ошибка отдельного элемента, общий снимок и продолжение каждого;
- отсутствие ГО/expiry остаётся неизвестностью; финансовые единицы согласованы по E13;
- старый формат сервера распознаётся как несовместимость, а не как пустой каталог;
- live-источник, внутреннее SDK-разрешение UID и действующий экспорт не регрессируют.

Для проверки из корня My_roBot после реализации:

```bash
.venv/bin/python -m pytest tests/unit/test_emulator_client.py tests/unit/api/test_instruments.py tests/unit/test_preflight.py tests/unit/test_cache_history.py tests/integration/test_historical_run.py
```

Это перечень требуемых проверок, а не отчёт об уже выполненном переходе.
Готовность означает работу исторического прогона с целевым сервером и сохранение
семантики кадров, прогрева, метаданных и закрытых баров, а не только замену URL.
